# Performance baseline

What `mid` costs today, measured before anything is optimised — #36. The
numbers below are a dated observation of one commit on one machine, not a
target and not a promise. Re-run `./docs/performance/measure.sh` to take
another; it prints the commit, the version and the machine at the top, so a
second reading can be compared with this one without either being edited.

Nothing in this repository has been optimised on the strength of this file.
What it establishes is that there **is** a real problem and **where** it is,
which is what #36 asked for and the whole of what it asked for.

## The two workloads

**Sparse** is `fixtures/olivia.mid` — 365 bytes, three tracks, 36 notes, no
control changes. It is already the reference Take, so nothing new is committed
for it and nothing about it can drift away from what the tests use.

**Dense** is generated by `dense-take.py`, deterministically: 200 Bars of 4/4
at 480 PPQ, four voice tracks, 6,400 notes, and 25,596 control changes — one
CC11 every eighth note on every voice track, on a curve that reverses, because
a reading built for a monotone rise is a reading that has not met a fader. The
file is 150 kB and its only content is repetition, so the recipe is committed
and the file is not. `measure.sh` prints its SHA-256, and two runs on two
machines produce the same bytes.

The proportions are the point: **four control changes for every note.** That is
what a densely automated DAW export looks like, and both `inspect` and `diff`
walk every one of them to answer a question about what is in force.

## The reading

Taken on **2026-09-07**, at `b82c3b0` (`mid 0.1.2`), on an Apple M1 under
Darwin arm64, release build. `play` is measured through a fake `fluidsynth`, so
what is timed is the passage `mid` prepares rather than somebody's soundfont.

| path | wall (s) | peak (MB) |
| --- | --- | --- |
| sparse `inspect` | 0.00 | 2.4 |
| sparse `inspect --json` | 0.00 | 2.3 |
| sparse `apply` (no-op Edit Set) | 0.00 | 2.2 |
| sparse `diff` (against itself) | 0.00 | 2.3 |
| sparse `play --bars 1:4` | 0.16 | 2.4 |
| dense `inspect` | 0.46 | 15.8 |
| dense `inspect --json` | 0.41 | 13.9 |
| dense `apply` (no-op Edit Set) | 0.00 | 3.9 |
| dense `diff` (against itself) | 0.33 | 8.8 |
| dense `play --bars 1:4` | 0.01 | 7.1 |

Memory is unremarkable everywhere: 16 MB at worst, for a 150 kB file held as
an owned `Smf` plus the readings taken off it. Nothing here scales in a way
worth watching.

## The scaling probe, and what it found

`measure.sh --scaling` turns two dials one at a time — the notes alone, then
the control changes alone — at three sizes. A path whose cost doubles when its
input doubles is linear; one that quadruples is not.

| | `inspect` (s) | `diff` (s) |
| --- | --- | --- |
| 200 Bars, notes only (6,400 notes) | 0.01 | 0.00 |
| 400 Bars, notes only (12,800 notes) | 0.02 | 0.01 |
| 800 Bars, notes only (25,600 notes) | 0.05 | 0.02 |
| 200 Bars, controls only (25,596 CC) | 0.35 | 0.33 |
| 400 Bars, controls only (51,196 CC) | 1.35 | 1.28 |
| 800 Bars, controls only (102,396 CC) | 5.20 | 5.53 |

**The notes are linear. The control changes are quadratic**, at about 3.7× per
doubling on both commands. 25,600 notes cost 0.05 s; 102,396 control changes
cost five seconds, and a Take twice that size would cost twenty.

That is not a hypothetical file. A four-minute orchestral export with recorded
expression, breath and pedal on a dozen channels reaches six figures of control
changes without trying, and this is the only shape of input in the corpus #35
will source that can.

### Where it is

Read from the code, and consistent with the probe attributing the whole of it
to the control changes:

- **`diff::controller_differences` → `held`** (`src/diff.rs`). For each
  `(channel, controller)` pair the moments compared are every Tick either Take
  says anything at, and `held` answers each one by filtering the whole
  statement list from the start. One statement per moment, one full scan per
  answer: O(*statements*²) per pair. `program_differences` → `in_force` has the
  same shape and does not matter, because a Take states a handful of Programs
  and tens of thousands of control changes.
- **`Take::unranked`** (`src/unranked.rs`). `for state in &stated { for other
  in &stated { … } }`, plus a `found.contains` inside. O(*statements*²) again,
  and it runs on every `inspect` whether or not anything is unranked.

Both are the same mistake: a question about *what is in force at a moment*
answered by re-reading the whole list, where the list is already in Tick order
and one walk would answer every moment in it.

### What has not been done about it

Nothing, deliberately. #36 says to optimise only where the measurement reveals
a release-relevant problem, and whether five seconds on a file this repository
has never been handed is release-relevant for 0.1.3 is a judgement about scope
rather than a fact about the code. Both fixes are ordinary — a merge walk in
step with the moments for the first, a Tick-keyed grouping for the second — and
neither is a redesign; both are also two more readings changed in a release
whose narrative is about truthfulness rather than speed.

Whoever picks this up should open its own issue and cite this file for the
evidence. Do not optimise anything not named above: nothing else in this
reading is scaling badly, and the sparse workload — which is what every test in
this repository and every audition so far actually runs — is at the floor.
